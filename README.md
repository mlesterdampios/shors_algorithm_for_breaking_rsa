# Shor's Algorithm for Breaking RSA — Reproducible Walk-Through

This repository contains a small, reproducible educational walk-through of RSA,
classical factoring, and a toy demonstration of Shor's algorithm against a very
small RSA modulus.

The goal is **not** to claim a practical break of real RSA keys. The notebooks
show the mechanics of the attack path using a deliberately small example
(`N = 15`) so that the full workflow can be inspected, reproduced, and compared
between classical and quantum-style approaches.

## Repository contents

```text
01_alice_bob_rsa.ipynb
02_eve_classical.ipynb
03_eve_quantum.ipynb
A Reproducible Walk-Through of RSA.pdf
rsa_public.json
```

### `01_alice_bob_rsa.ipynb`

Builds the toy RSA setting used throughout the project.

It demonstrates:

- RSA key generation using small primes.
- Public and private key construction.
- Encryption and decryption of a small integer message.
- How RSA exponentiation can be viewed as a modular permutation.
- Export of public RSA values to `rsa_public.json`.

### `02_eve_classical.ipynb`

Shows how an attacker can recover the private key classically when the modulus is
very small.

It demonstrates:

- Loading the public RSA values from `rsa_public.json`.
- Factoring the toy modulus using classical methods.
- Reconstructing Euler's totient.
- Recovering the private exponent.
- Decrypting the ciphertext without Alice's private key.

### `03_eve_quantum.ipynb`

Shows the same toy attack path using a small Shor-style demonstration.

It demonstrates:

- A small-period-finding example for `N = 15`.
- Local noiseless simulation using Qiskit Aer.
- Optional execution on IBM Quantum hardware through Qiskit Runtime.
- Classical post-processing of measurement results into candidate factors.
- Reconstruction of the RSA private key after recovering the factors.

Hardware results are expected to vary because real quantum devices are noisy,
calibrations change, queues vary, and available backends may differ by account.

### `A Reproducible Walk-Through of RSA.pdf`

Compiled paper describing the motivation, background, methodology, results, and
limitations of the demonstration.

### `rsa_public.json`

Shared public RSA values generated by Notebook 1 and consumed by the later
notebooks.

## Recommended execution order

Run the notebooks in this order:

1. `01_alice_bob_rsa.ipynb`
2. `02_eve_classical.ipynb`
3. `03_eve_quantum.ipynb`

Notebook 1 should be run first because it creates or refreshes
`rsa_public.json`.

## IBM Quantum hardware run

The hardware portion of `03_eve_quantum.ipynb` requires an IBM Quantum account
and API token.

The notebook contains this placeholder:

```python
IBM_TOKEN = 'XXXXX'
```

Replace it locally with your own token when running the notebook, but **do not
commit a real token to the repository**.

For a cleaner setup, you may modify the notebook to read the token from an
environment variable instead:

```python
import os
IBM_TOKEN = os.environ["IBM_QUANTUM_TOKEN"]
```

Then run:

```bash
export IBM_QUANTUM_TOKEN="your-token-here"
```

On Windows PowerShell:

```powershell
$env:IBM_QUANTUM_TOKEN="your-token-here"
```

## Scope and limitations

This project is intentionally limited.

- The RSA modulus is tiny and insecure by design.
- The example is for learning and reproducibility, not practical cryptanalysis.
- The quantum demonstration uses a small, structured instance suitable for
  inspection.
- Successful execution on real hardware does not imply that current quantum
  computers can break real RSA keys.
- Larger RSA keys require fault-tolerant quantum computers with far more logical
  qubits and much lower effective error rates than current noisy devices.

## Reproducibility notes

The classical notebooks should be deterministic for the included toy example.

The quantum notebook has two paths:

- **Local simulator path:** should be reproducible on a correctly configured
  local environment.
- **IBM hardware path:** may vary across runs because of backend availability,
  calibration, queue state, transpilation, and device noise.

If the hardware run does not recover the expected factors from the top
measurements, rerun the job, increase the number of shots, or select another
available backend.
